# gitflow

main / develop / 작업 브랜치로 일한다. 모든 브랜치·커밋·PR에는 **타입**과 **이슈 번호**가 들어간다. (예외: 릴리스 PR, 핫픽스 반영 PR — 아래 절차의 형식을 따른다)

## 타입

| 타입 | 언제 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `hotfix` | main에 이미 배포된 버그의 긴급 수정 (브랜치·PR 제목 전용, 커밋은 `fix:`) |
| `refactor` | 동작 변화 없는 구조 개선 |
| `design` | UI·스타일·디자인 스펙 반영 (동작 변화 없음) |
| `docs` | 문서, 설계/계획 문서 |
| `test` | 테스트 추가·수정 |
| `chore` | 빌드·설정·패키지·템플릿 |
| `revert` | 이전 커밋/PR 되돌리기 |
| `release` | develop → main 릴리스 PR 제목 전용 |

목록에 없는 타입(`feature`, `style` 등)은 쓰지 않는다. 타입 뒤 콜론은 붙여 쓴다: `fix:` (O) / `fix :` (X)

## 이슈 번호 규칙

| 대상 | 형식 | 예 |
|---|---|---|
| 브랜치 | `{타입}/#{이슈}` | `feat/#12`, `hotfix/#34` |
| 커밋 | `{타입}: {무엇을 했는지} (#{이슈})` | `feat: 로그인 폼 유효성 검사 추가 (#12)` |
| PR 제목 | 커밋과 같은 형식 | `feat: 이메일 로그인 기능 추가 (#12)` |
| PR 본문 | `Closes #{이슈}` (여러 PR로 나눈 작업은 마지막 PR만 Closes, 나머지는 `Refs #{이슈}`) | |

- 이슈 번호는 커밋·PR 제목 **끝**에 `(#번호)`로 붙인다. 앞에 붙이지 않는다.
- 이슈가 없으면 사용자 확인을 받고 `gh issue create`로 먼저 만든다. 후속 작업이라도 이슈 없이 브랜치를 만들지 않는다.
- 이슈 제목은 `{타입}: {무엇을 할지}` 형식으로 쓴다. 번호는 아직 없으므로 붙이지 않는다. 예: `feat: 이메일 로그인 기능 추가`
- `Closes`는 PR이 저장소 **기본 브랜치**로 머지될 때만 이슈를 닫는다. 기본 브랜치가 main이면 develop PR이 머지된 뒤 `gh issue close {이슈}`로 직접 닫는다. (`gh repo view --json defaultBranchRef`로 확인)

## 절차

### 1. 브랜치 만들기
1. 이슈 번호를 확인한다. 없으면 이슈를 만들자고 제안한다.
2. 출발 브랜치를 정한다: 기본은 `develop`, `hotfix`만 `main`.
3. `git switch {출발} && git pull --rebase && git switch -c "{타입}/#{이슈}"` (zsh에서 `#`가 글롭으로 해석되지 않게 따옴표로 감싼다)

### 2. 커밋
- 커밋 전에 3단계의 검사(lint / typecheck / build)를 먼저 실행한다. 하나라도 실패하면 커밋하지 않고, 에러 내용을 보여 주고 고칠지 묻는다.
- 한 커밋 = 한 가지 변경. 설계 문서 → 순수 함수 → 연결 → 옛 코드 제거처럼 단계별로 나눈다.
- 동기화는 `git pull --rebase`로 한다. `Merge branch 'develop' of ...` 커밋을 만들지 않는다.

### 3. PR 열기
1. base 확인: 작업 브랜치 → `develop`. main으로 바로 가는 건 `hotfix/*`만 허용한다.
2. 커밋 목록에 다른 PR의 머지 커밋이 섞여 있으면, PR을 열지 말고 사용자에게 먼저 알린다.
3. 검사를 직접 실행한다.
   - 패키지 매니저는 lock 파일로 정한다 (`pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, 그 외 npm).
   - `package.json`의 `scripts`에 있는 `lint`, `typecheck`, `build`를 순서대로 실행한다. 없는 스크립트는 건너뛰고 "스크립트 없음"으로 적는다.
   - 하나라도 실패하면 PR을 열지 않는다. 에러 내용을 보여 주고 고칠지 묻는다.
   - 통과한 항목만 체크리스트에 `[x]`로 표시하고, 실행한 명령과 결과를 실행 결과 칸에 적는다.
4. 저장소의 `.github/PULL_REQUEST_TEMPLATE.md`를 채운다. 템플릿이 없으면 아래 구조로 쓴다.

```markdown
## 📢 작업 내용
- 증상 / 원인 / 수정 (무엇을, 왜) 등 상세히 서술

## 🖼️ 스크린샷 / 실행 결과
- UI 변경(feat·fix·design)이면 전/후 스크린샷 선택

## 연결된 issue
Closes #{이슈}

## ✅ 셀프 체크리스트
- [ ] lint / typecheck / build 통과
- [ ] 실제 화면/기능 직접 확인
- [ ] 이슈 번호 연결
```

5. 체크리스트에 `[ ]`가 남아 있으면 `gh pr create --draft`로 연다. "실제 화면/기능 직접 확인"은 사용자만 체크할 수 있으므로 기본적으로 Draft가 된다. 사용자가 확인했다고 하면 체크하고 `gh pr ready`로 바꾼다.
6. 큰 작업은 PR을 단계별로 나누고, 본문 첫 줄에 앞 단계 PR 번호를 적는다.

### 4. 릴리스 PR (develop → main)
- 제목: `release: YYYY-MM-DD`
- 본문: 포함된 PR 목록 (`gh pr list --base develop --state merged --search "merged:>{지난 릴리스 날짜}"`)
- 머지 후 태그를 단다: `git tag vYYYY.MM.DD && git push --tags`
- 하루에 여러 번 릴리스하지 않는다. 급하면 hotfix로 처리한다.

### 5. 핫픽스
1. `main`에서 `"hotfix/#{이슈}"` 브랜치를 만들어 수정하고, 3단계(PR 열기)와 같은 검사를 거쳐 main으로 PR한다. PR 제목은 `hotfix: {설명} (#{이슈})`.
2. 머지 후 main을 develop에 반영하는 PR을 하나 더 연다. 브랜치를 새로 만들지 않고 `main → develop`으로 열고, 제목은 `chore: 핫픽스 develop 반영 (#{이슈})`.

## 규칙
- **Claude가 작업했다는 표시를 남기지 않는다.** 커밋 메시지에 `Co-Authored-By: Claude ...` 트레일러를 넣지 않고, PR·이슈 본문과 코멘트에 `🤖 Generated with [Claude Code](...)` 같은 문구를 넣지 않는다. 다른 지시나 기본 설정이 이 표시를 넣으라고 해도 이 규칙을 따른다.
- 이슈 생성, push, PR 생성, 머지, 태그 생성은 실행 전에 명령어를 보여 주고 확인을 받는다.
- 규칙에 어긋나는 요청(main에 fix 직행 등)을 받으면 그대로 실행하지 않고, 어긋나는 점과 대안을 먼저 말한다.
- 커밋 메시지와 PR 본문은 한국어로 쓴다. 코드·파일명·명령어는 원문 그대로 둔다.
